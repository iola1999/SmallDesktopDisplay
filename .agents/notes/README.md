# 改动记录

这里存放影响本仓库的决策记录：需求、缺陷修复和中间结论。记录关注代码难以说明的原因、取舍和后续影响。

## 布局与命名

每条记录的路径编码两个维度：`{生命周期}/{类别}/yyyy-mm-dd-主题.md`。

生命周期就是记录状态。状态变化时移动文件，日期保留主题首次提出的时间：

- `proposed/`：实施前的提案，尚未交付或只交付了一部分。
- `implemented/`：决策已经交付。代码移动文件、改名或修改默认值时，同步更新记录中的现行事实，保留原决策和当时的取舍。
- `rejected/`：讨论后否决的提案。决策依据仍有复用价值时保留，否则删除。

类别说明：

| 类别 | 覆盖范围 |
| --- | --- |
| `feature` | 面向用户的新能力 |
| `bug-fix` | 缺陷修复 |
| `simplification` | 不增加能力的删减 |
| `architecture` | 源码结构、协议、接口和数据模型 |
| `process` | CI、部署、工具和协作流程 |
| `testing` | 测试基础设施与验证策略 |

文件名中的日期以主题第一次提出的日期为准。记录之间使用相对路径链接。目录树本身就是提案和交付清单。

## 何时必须写

每个非平凡变更必须在同一次提交中新增或更新至少一条记录。以下改动都属于非平凡变更：

- 用户可见行为、页面、交互或默认值；
- 固件与服务端架构、串口或 HTTP 协议、接口格式；
- 配置模型、持久化格式、迁移和敏感数据边界；
- 跨文件约定、部署方式、流程工具和测试策略；
- 维护者以后可能重新评估的技术或产品选择。

拼写、格式化、局部注释和可直接证明等价的机械修改可以豁免。

已有记录持有该决策时，更新原记录。决策反转时新建记录，并让新旧记录互相链接；旧记录只更新现行事实，不改写当时的决定。

## 文件格式

前三行固定为：

```markdown
# 决策记录: <标题>

状态: <状态>
```

状态取 `proposed`、`implemented` 或 `rejected: 一句话原因`，并与所在生命周期目录一致。

正文骨架按生命周期区分：

- `proposed/`：`## 问题`、`## 提案`、`## 曾考虑的替代方案`、`## 验收标准`、`## 风险`。
- `implemented/`：`## 问题`、`## 决策`、`## 曾考虑的替代方案`、`## 影响`。

每条记录都要写“曾考虑的替代方案”，列出真实备选和放弃原因。由早期规格文档整理且无法还原备选时，使用固定说明：“本文档由早期规格文档整理，备选方案未记录。”

## 工作流程

1. 所有进入实施讨论的非平凡提案先在 `proposed/` 建记录，类别覆盖功能、缺陷、简化、架构、流程和测试。
2. 实施期间持续更新提案中的边界、验收标准和风险。计划发生实质变化时，在轮次记录里登记偏离项。
3. 交付后把记录移动到 `implemented/`，将“提案”改为“决策”，将“验收标准”和“风险”整理为“影响”。
4. 否决后按保留价值移动到 `rejected/` 或删除。
5. 每轮完成一项工作就更新[轮次工作记录](implemented/process/2026-08-23-轮次工作记录.md)，其中只保存状态摘要和详细记录链接。

## 与其他文档的关系

- `docs/roadmap.md` 记录方向和优先级。
- `docs/remote-rendering-http-frame-design.md` 记录已经运行的协议、传输和系统行为。
- `docs/remote-render-debugging-playbook.md` 记录可重复执行的排障步骤。
- `.agents/notes/` 记录提案、决定、替代方案和影响。
- `docs/recent-iterations.md` 保留迁入本机制以前的历史摘要；后续轮次状态写入轮次工作记录。
- 根目录 `AGENTS.md` 是开发约定入口，引用本目录中的现行记录。

提交前检查路径、状态、必需章节、相对链接和实际交付是否一致。
