# 决策记录: 控制台实时同步与版本历史

状态: implemented

## 问题

控制台基础版要求用户先修改草稿，再从页面底部提交。这个流程延迟了设备更新，也让配置与亮度的部分成功、设备切换和修订冲突变得难以理解。保存请求返回时，期间产生的新操作还可能被旧响应覆盖。

页面布局也有几个直接影响使用的问题。首页设置纵向堆叠后超过视口，底部操作区继续增加页面高度；开关的文字样式同时命中了轨道，圆点沿纵轴移动。多处圆角、描边和明显阴影削弱了信息层级。

## 决策

配置修改先更新本地画面，静置 160 毫秒后发送 `PATCH`。亮度使用独立队列，静置 120 毫秒后发送设备命令。每条队列同一时间只发送一个请求，控件在请求期间保持可用。配置响应会按本次发送值合并后续操作，亮度响应只确认本次发送值；队列仍有新值时继续发送。

服务端返回 `409` 时，控制台读取最新配置，按字段合并本地操作，再使用新 ETag 发送。连续三次冲突或其他写入错误会暂停当前队列，界面显示失败原因和重试入口。用户把失败操作恢复到服务端基线时，相关错误和失败签名自动清除。同步结束前选择其他设备时，控制台先记住目标设备，完成当前写入后再切换。

发布用于创建人工确认的稳定版本。历史侧栏只显示发布版本，并允许回退到任意仍保留的版本。回退把所选版本设为当前配置并增加全局修订号，已发布版本保持原样。发布和回退共用一个操作状态，执行期间暂停配置自动同步和设备切换。版本请求发生冲突时，控制台按请求中的设备 ID 读取最新配置；缓存和本地状态都会拒绝较旧的修订响应。亮度由设备 EEPROM 持有，不进入服务端配置历史；配置文件只读时，亮度控制仍可发送设备命令。

新增接口：

- `GET /api/v1/devices/:id/config/history`
- `POST /api/v1/devices/:id/config/publish`
- `POST /api/v1/devices/:id/config/rollback`

历史快照保存在 `STATE_DIR/remote-render-config-history/`。目录权限为 `0700`，文件权限为 `0600`。每次发布写入一条快照，最多保留最近 100 个发布版本。自动同步和回退更新主配置文件与全局修订号，配置修订可以高于最新发布版本。历史目录缺失或为空时，下一次发布会重新创建目录。启动时会清理旧格式中未发布的快照，已发布版本和当前配置保持原样。文件损坏或写入失败会将配置存储置为只读。历史接口从存储层的一次同步读取中返回 `currentRevision`、`currentConfig` 和发布版本。

控制台根节点固定为 `100dvh`，浏览器页面不产生纵向或横向滚动。桌面端保持导航、编辑和预览三栏；窄屏按导航、预览和编辑区排列。编辑区、导航、预览和历史列表在空间不足时独立滚动。首页、外观和诊断使用可换行的 flex 容器，选项按剩余宽度自动伸缩。

界面继续使用中性灰和单一青绿色。结构区依靠背景层级与细分隔线，控件圆角收至 2 至 4 像素。常规页面没有阴影；提示条只保留 `0 2px 8px` 的浅阴影。开关轨道固定为横向 `32 x 18`，圆点固定为 `14 x 14`。

## 曾考虑的替代方案

- 每次输入事件立即写盘：拖动亮度和快速切换选项会产生大量重复请求，短防抖可以合并连续操作。
- 配置与亮度共用一条请求：两种状态的持久化位置和失败方式不同，独立队列可以分别确认与重试。
- 把历史数组写进主配置文件：文件会持续增长，每次修改都要重写全部历史。独立快照便于限量保留，并能分别校验文件格式和当前修订。
- 在浏览器保存历史：清理站点数据或换一台电脑后记录会消失，也无法支持多个控制台。

## 影响

- 首页、外观和亮度操作在本地立即反馈，并自动作用于设备。
- 页面顶部显示正在同步、实时生效或同步失败；发布按钮只在配置同步完成后可用。
- 保存期间继续修改、改回原值和较旧查询晚到都有 reducer 测试。
- 服务端测试覆盖发布、回退、旧快照清理、损坏历史、文件权限、写入失败、修订号间隔和 100 个版本的保留上限。
- 历史抽屉只渲染发布版本。当前配置仍由历史接口原子返回，供控制台确认全局修订和回退请求使用。
- 真实 Chrome 已检查 `1440x900`、`1280x720` 和 `390x844`。三个视口的页面根节点尺寸都与视口一致，开关圆点、历史侧栏、发布和回退操作可以正常使用。
