# 决策记录: 建立非平凡改动与提案记录流程

状态: implemented

## 问题

仓库原有 `docs/recent-iterations.md`、路线图、设计文档和排障手册，但缺少统一的提案状态和决策格式。功能构想、实施取舍与当前行为容易写进同一份文档，后续很难确认一项内容仍在讨论、已经交付，还是已经放弃。

## 决策

参考 `etf-watch` 的做法，在 `.agents/notes/` 建立改动记录目录，规则见[改动记录说明](../../README.md)。

- 路径采用 `{生命周期}/{类别}/yyyy-mm-dd-主题.md`。
- 生命周期使用 `proposed`、`implemented` 和 `rejected`。
- 类别使用 `feature`、`bug-fix`、`simplification`、`architecture`、`process` 和 `testing`。
- 每个非平凡变更在同一次提交中新增或更新至少一条记录。
- 所有进入实施讨论的非平凡提案从 `proposed/` 开始。交付时移动记录并改写为已实施格式，否决时移动到 `rejected/` 或删除。
- [轮次工作记录](2026-08-23-轮次工作记录.md)只保存当前状态、验证结果和详细记录链接。

现有规格文档继续承担各自职责。本次不批量迁移旧历史，后续触及相关行为时再补充或更新对应记录。

## 曾考虑的替代方案

- 继续只维护 `docs/recent-iterations.md`：文件已经同时包含现状、历史、命令和排障信息，继续追加会让提案状态和决定依据更难查找。
- 在 `docs/proposals/` 单独建立编号提案：可以管理提案，覆盖不了缺陷修复、简化、测试和流程记录，也会形成两套分类规则。
- 所有修改都要求记录：拼写、格式化等机械修改会产生大量低价值文件，所以保留纯机械局部修改豁免。
- 引入脚本强制校验目录和章节：当前记录数量很少，先用提交前检查清单。记录增多后再评估自动校验。

## 影响

- `AGENTS.md` 增加记录要求和修改前阅读入口。
- 本轮控制台与内容页面构想先进入 `proposed/`，功能代码尚未修改。
- 以后修改现行协议、配置格式、页面行为和部署方式时，需要同步维护对应记录。
- 历史文档继续保留；新记录可以链接旧文档，减少重复抄写。
